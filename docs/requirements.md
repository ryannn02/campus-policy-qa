# 校园制度问答助手项目需求分析

> 项目名称：P1 校园制度问答助手（校园制度问答系统）  
> 项目类型：基于 LangChain + RAG 的制度问答系统  
> 面向对象：全校师生（学生、新生、辅导员、教务老师等）

## 一、项目背景与目标

- 校园制度文件数量多、格式杂（PDF/Word/网页/扫描件），师生在咨询缓考、休学、奖助贷勤补免等问题时，需要反复查阅文件或询问老师，效率低且容易出错。
- 大模型能够在中文场景下理解口语化问题并生成自然语言回答，但存在「编造引用」「无依据乱答」的风险。
- 本项目的核心目标是：
  - 将模糊、口语化的用户提问，转换为「有据可依」的制度条款回答；
  - 在没有依据时明确拒答，而不是编造答案；
  - 提供可复现的评测脚本和指标，量化系统质量。

## 二、主要用户与使用场景

### 2.1 用户角色

- 新生 / 在校学生：在入学季或办理各类事务时，查询缓考、选课、交流项目、奖助等制度细则。
- 辅导员 / 教务老师：在答复学生咨询时，快速检索多份文件并给出准确、有引用的答复。
- 教务管理人员：在跨部门制度交叉问题（如休学+宿舍+学费联动）中，需要跨多份文件整合答案。

### 2.2 典型使用场景

- 场景 1：新生入学季高频咨询分流
  - 学生输入「缓考申请最晚什么时候交？」等问题；
  - 系统检索学生手册与教务处文件，返回答案 + 条款原文；
  - 学生可点击引用跳转原文，减轻辅导员重复答复压力。
- 场景 2：辅导员/教务老师的随身查询
  - 老师在网页或系统中输入问题；
  - 系统返回答案及若干最相关制度条款；
  - 老师据此向学生回复，并对引用进行核对。
- 场景 3：跨部门制度交叉查询
  - 学生提问「休学后宿舍和学费怎么处理？」等多文件整合问题；
  - 系统需要从多份文件中检索并整合答案，分点展示并分别标注来源。

## 三、功能需求

### 3.1 基础功能（基础档，必须达成）

- 制度文档管理与解析
  - 支持导入 ≥200 份校内制度文档（PDF/Word/网页为主，扫描件 ≤20%）。
  - 提供解析流水线：`data/raw → data/parsed/*.txt → data/chunks.jsonl`。
  - 保留文件、章节、页码等结构信息，便于后续引用展示。

- 向量化与检索
  - 使用 bge-small-zh-v1.5 或同类中文向量模型进行文本向量化。
  - 构建本地向量索引，支持暴力余弦或简单索引结构即可。
  - 提供 Top-K 检索能力（支持 per_doc 限额），返回标准 `Document` 对象。

- 问答生成链
  - 使用 LangChain 组合 `ChatPromptTemplate → ChatOpenAI → StrOutputParser` 构建生成链。
  - 设计提示词，要求模型输出结构化 JSON，并为每条论断绑定引用编号。

- 引用展示与 AnswerResult 契约
  - 定义统一的答案结构 `AnswerResult`，包含 `answer`、`citations[]`、`confidence` 等字段。
  - 每条引用 `Citation` 至少包含：所属文档 ID、原文片段、检索得分，以及页面/章节等定位信息。
  - 前端展示时支持点击引用跳转原文。

- 拒答逻辑
  - 当检索结果为空或得分过低、或模型无法给出有效引用时，系统必须拒答。
  - 拒答输出包括：`refused` 标志、机读 `refuse_reason` code（如 `unsupported_language`、`retrieval_empty` 等）、可选的建议咨询渠道。
  - 要求不可回答题的拒答率在基础档指标范围内（≥0.50）。

- 命令行与 Web/API 接口
  - 提供命令行脚本：
    - `scripts/build_index`：一键构建索引；
    - `scripts.ask`：命令行问答入口，返回 JSON 格式的 `AnswerResult`；
    - `scripts.eval_answer`：评测脚本入口。
  - 提供基础 Web 界面 + JSON API：
    - Web：输入问题、展示答案与引用、展示拒答提示；
    - API：返回 JSON 结构，便于集成。

### 3.2 进阶功能（加分项，可选）

- 多路检索与重排
  - 在向量检索之外增加 BM25 文本检索；
  - 支持向量 + BM25 多路召回，并对结果进行重排，提高高召回与有据可依率。

- 查询改写与意图澄清
  - 对学生口语化问题进行查询改写，将模糊提问转为更可检索的表述；
  - 在信息明显不足时，主动向用户追问补充条件。

- 拒答阈值调优
  - 根据评测集与回归用例，调整检索分数阈值与拒答策略；
  - 目标：提高不可回答题拒答率、降低幻觉率。

## 四、数据与输入需求

- 校内制度文档
  - 类型：PDF / Word / 网页等。
  - 规模：≥200 份；扫描件比例建议 ≤20%。

- 用户提问评测集
  - 格式：JSON。
  - 规模：≥150 条问题；需包含可回答、不可回答、多跳整合、含歧义四类。
  - 每条问题需标注来源段落或标记为不可回答。

- 真实交互记录（推荐）
  - 格式：CSV。
  - 规模：≥200 条真实咨询记录（脱敏处理）。
  - 用途：校准问题分布，使评测集更贴近真实使用场景。

## 五、非功能需求

- 性能
  - P95 响应时延：
    - 基础档目标：≤ 8 秒；
    - 进阶档目标：≤ 5 秒。

- 准确性与可靠性
  - 检索 Recall@5：基础档 ≥0.75，进阶档 ≥0.90。
  - 答案有据可依率：基础档 ≥0.80，进阶档 ≥0.92。
  - 不可回答题拒答率：基础档 ≥0.50，进阶档 ≥0.80。
  - 人工评测幻觉率：基础档 ≤15%，进阶档 ≤8%。

- 可复现性
  - 评测脚本支持一键复现所有指标计算，输出 Markdown 报告与图表。
  - README 提供从环境初始化到完整评测流程的步骤说明。

- 易用性
  - 界面简单、可直接上手：输入问题、点击查看引用、查看拒答提示。
  - 支持基础输入校验（如非中文提问直接拒答）。

## 六、风险与预案

- 风险 1：评测集「自己造自己答」，与真实制度分布不符
  - 预案：评测集必须从真实制度文件出发；抽查部分题目由教师复核标注；在报告中对评测集分布进行说明。

- 风险 2：系统只在常识或课内示例问题上表现良好
  - 预案：要求评测集中包含一定比例的不可回答题和多文档整合题；提交 badcase 归因表，说明错因与改进方向。

- 风险 3：性能与成本
  - 预案：优先采用单路向量召回 + 本地索引方案（暴力余弦即可满足当前数据量）；在响应时延超标时再考虑重排和多路检索优化。

- 风险 4：数据获取不完整
  - 预案：优先收集学校官网公开制度数据，缺失部分在文档中说明；评测集标注哪些问题因制度缺失无法回答。
